2026-05-03 staging/batch materialization 排列方式结论：
- “把存活 object 先放在相同地方紧凑排列，再用 non-temporal store 传输”可以实现，但 staging 不能成为对象语义地址。
- forwarding pointer 必须仍然指向最终 old address；root、RS、function table slot、young object 内部字段都必须 patch 到最终 old address。
- 最稳妥的第一版是 materialization queue：`copy_for_minor` 分配最终 old address 并设置 forwarding pointer；traversal 阶段 patch young object；对每个 live object 记录 `(young_src_hdr, old_dst_hdr, aligned_size, type)`；最后统一 materialize。
- 推荐排列方式是 old destination order，也就是 forwarding pointer 分配顺序。这个顺序让 old address 单调递增，写 old 天然连续，不需要排序，也最容易保持当前 GiY 的语义正确。
- 第一版可以先不做真正 staging，只把当前“边扫描边 copy”改成“先记录 queue，最后按 old address 顺序 copy/NT”。
- 如果要做真正 staging，建议用 32KB 或 64KB cache-line aligned staging slab，按 old destination order 把 live objects 紧凑打包，slab 满后再按相同顺序写回 final old address。
- 第二阶段可以尝试 size-class bucket，例如 `<=256`、`257-512`、`513-1024`、`>1024`；小对象继续 memcpy，大对象 bucket 用 NT/staging。这个方案可能改善 CD/Havlak，但需要先规划 bucket 大小再设置 forwarding pointer，复杂度更高。
- 不推荐把 forwarding pointer 指向 staging，也不推荐小对象全部 staging 后统一 NT。之前完整 suite 统计显示小对象按 count 占绝对多数，小对象 memcpy 更有数据支持。
- 最建议路线：先实现 old-order materialization queue；再只对 `>256` 对象启用 batch/NT；如果仍有收益空间，再引入 staging slab；最后再考虑 size-class bucket。

2026-05-03 当前 Practical GiY GC 与 Cheney GC 对比结论：
- 这里把“当前 GC”理解为当前仓库中的 Practical GiY minor GC，把 Cheney GC 理解为标准 Cheney-style copying GC / 仓库中的 `cache_cheney` 对照思路。
- Cheney GC 的核心是复制对象到目标空间后，从目标空间继续扫描；scan 指针和 copy/free 指针线性推进，优点是简单、成熟、正确性容易维护。
- 当前 Practical GiY 的核心是对象图遍历和字段修正在 Young/Cache 内完成，最后才 materialize 到 Old/DRAM；目标是减少 minor GC 强扫描阶段对 Old/DRAM 的读取和 cache pollution。
- Cheney 会在扫描已复制对象时读取目标空间对象字段；如果目标空间是 DRAM/Old，就会带来 DRAM read。GiY 则尽量只读 Young/Cache 中的对象字段。
- Cheney remembered set 通常只需要记录 old slot 地址，GC 时读 slot 当前值；GiY remembered set 额外保存最近写入的 value，目的是扫 RS 时不读 old slot。
- Cheney 更容易复用通用 root/function table scan；GiY 不能全表扫描 function table，因此当前用 function table strong slot set 记录真正可能指向 Young 的强 slot。
- Cheney 的 copy 策略通常直接 memcpy 即可；当前 Practical GiY 使用 `<=256 bytes memcpy`、`>256 bytes non-temporal store`，因为完整 allocation profile 显示小对象按 count 占绝大多数。
- 性能上，当前 GiY 相比旧 GiY 已大幅降低 GC full/scavenge；相比 cache_cheney，GC core 已更快，但总时间仍接近或略慢，剩余问题主要在 RS patch、write barrier、cache locality、mutator-side 影响。
- 一句话总结：Cheney GC 是“复制后扫描新空间”的简单可靠基线；当前 Practical GiY 是“先在 Cache/Young 内扫描和修指针，最后写 Old/DRAM”的架构优化版本。GiY 更复杂，但更符合避免 Old/DRAM read 和降低 cache pollution 的研究目标。

## 2026-05-03 business/non-GC time 增加 48.986s 的原因调查与验证

结论：这 `+48.986s` 不是 GC core 变慢。GiY GC core 比 Cheney 少 `34.118s` / `37.93%`，但 business/non-GC 多 `48.986s`。主因集中在 Havlak/CD：Havlak 多 `35.329s`，贡献 `72.12%`；CD 多 `6.078s`，贡献 `12.41%`；两者合计解释 `84.53%`。

已验证不是 benchmark 迭代数或 allocation-size profile 噪音：关键 benchmark 两边都是 `iterations=100`，out29 没有使用 `ALLOC_SIZE_PROFILE=true`。

验证 1：GiY active young area 更小，解释普遍 minor GC +13.9%。GiY `Young before aux=300.24KB`，`Young after aux=230.72KB`，aux 占 `69.52KB`。Cheney 估算 active young 约 `262.71KB`，因此预测 minor GC 增加 `13.865%`；实测 Bounce/List/Storage/Mandelbrot/NBody 等 allocation 基本相同的 workload minor GC 增加约 `13.90%`。

验证 2：真正解释 Havlak/CD business 增量的是 GiY write barrier 的 remembered-set value-update 线性扫描。GiY 为了保存 old/init slot 最新 young value，在 immediate/old/null 写入时会调用 `rememberset_update_existing(slot, 0)` 清除旧 value；当前实现线性扫描 `remembered_set.buffer`。这发生在 write barrier 内，记入 business/non-GC time，而且现有 `Write barrier calls` 不统计这些 clear/update 扫描。

我加了默认关闭的 `GIY_WB_PROFILE=true` 验证开关，只跑 CD/Havlak：
- CD：`Update attempts=43,851,721`，`Update scan steps=401,694,113`，`Steps/attempt=9.160`，`Clear attempts=40,851,797`，相当于每个已计数 WB call 额外 `41.96` 次线性扫描 step。
- Havlak：`Update attempts=444,200,570`，`Update scan steps=190,916,727,113`，`Steps/attempt=429.798`，`Clear attempts=417,674,314`，相当于每个已计数 WB call 额外 `1157.07` 次线性扫描 step。

因此当前最明确的原因是：GiY 的 RSet `values[]` 清理/更新路径把大量 mutator-side write barrier 工作变成了线性扫描，尤其 Havlak 达到约 `1909亿` 次扫描 step，直接对应它 `+35.329s` 的 business regression。

次要因素：Havlak allocations 多 `172,780,795` / `9.30%`，CD allocations 多 `215,155,165` / `10.25%`；两边都是 100 iterations，所以这更可能来自 GC 时机影响 VM/runtime cache、shape、inline cache、weak metadata 等对象生命周期。

修复建议：优先把 `rememberset_update_existing` 改成 hash-probe 后 O(1) 更新，例如 hash table 存 buffer index 或维护并行 index table；duplicate/update 时直接写 `values[index]`，并处理 `HASH_PROBE_LIMIT` fallback，避免只能线性找。修完先重跑 Havlak/CD/Storage，再跑 full suite。
